# cpu-bench

Windows PC용 무료 진단형 CPU 벤치마크. 점수만 보여 주는 게 아니라 **내 PC가 제 성능을 내는지, 왜 이 점수인지, 뭘 하면 나아지는지**까지 알려 주는 것이 목표입니다.

## 내려받기

**[최신 버전 받기 (Releases)](https://github.com/song-circle/devlog-kr/releases?q=cpu-bench)** — `cpu-bench-<버전>-win-x64.zip`을 받아 압축을 풀고 `cpu-bench.exe`를 실행하면 됩니다. 설치는 필요 없습니다(Windows 10/11 x64).

- 아직 코드 서명 인증서가 없는 초기 버전이라 처음 실행할 때 "Windows의 PC 보호" 창이 뜹니다. **[추가 정보] → [실행]**을 누르세요. 받은 파일이 원본인지는 릴리스 페이지의 SHA-256 값으로 확인할 수 있습니다.
- PC 측정 결과는 이 PC에만 저장하고 어디에도 보내지 않습니다. 켤 때 GitHub에 최신 버전 번호만 물어보고, 새 버전이 있으면 알려 줍니다(화면 아래에서 끌 수 있음).
- **인터넷 속도 측정(선택)**은 M-Lab 공개 측정 서버를 씁니다. 이 측정의 결과와 공인 IP 주소가 M-Lab 공개 연구 데이터로 남기 때문에, 처음 누를 때 동의를 받고 버튼을 누를 때만 통신합니다.
- 지금 들어 있는 것: 제 성능 발휘율 %, 한눈에 보는 상태(발열·성능 유지, 메모리 이론 속도 대비, 쉴 때 CPU 사용, 전원 설정, 그래픽카드·SSD·랜 연결), 싱글 측정 중 코어 클럭, 인터넷 속도(선택, M-Lab)와 전체 점검 버튼, 점수(싱글·멀티), 환경 점검(전원 설정, 메모리 채널·XMP, 백그라운드 프로그램), 1분 발열 검사. 점수 밖 측정으로 부동소수점(행렬곱·물체 인력 계산)과 멀티코어(스레드 확장 곡선, 거짓 공유 등 동기화 비용)가 있습니다. 부하 모듈은 정수·메모리·부동소수점·동기화 네 개입니다.

배포본 만들기: `powershell -ExecutionPolicy Bypass -File cpu-bench\packaging\package.ps1` (버전은 [VERSION](VERSION) 파일 하나에서 읽음)

## 구조

```
[제어 앱 (예정)] ── Named Pipe(JSON) ──> [측정 러너 cpu-bench-runner.exe] ── LoadLibrary ──> [부하 모듈 bench_*.dll]
```

- **러너**는 측정만 하는 별도 프로세스입니다. 우선순위 HIGH(REALTIME은 쓰지 않음), 스레드를 코어에 고정하고, 하이브리드 CPU에서는 싱글 스레드 측정을 성능 코어(P코어)에서 합니다.
- **부하 모듈**은 공통 C 인터페이스([include/bench_api.h](include/bench_api.h))를 구현한 DLL입니다.
- 측정 절차: 워밍업 1회 → N회 측정 → **중앙값** 채택, 회차 간 편차(CV)가 2%를 넘으면 경고.

## checksum으로 하는 두 가지 검증

모듈은 같은 입력으로 같은 계산(작업 단위)을 반복합니다. 그래서 결과값(checksum)은 항상 같아야 합니다.

1. **계산이 실제로 일어났는지**: 결과가 기대값과 맞아야 합니다. 같은 계산을 Python 표준 라이브러리로 따로 구현한 [tools/int_reference.py](tools/int_reference.py), [tools/mem_reference.py](tools/mem_reference.py)와 결과를 비교합니다.
2. **PC가 안정적인지**: 반복 도중 결과가 한 번이라도 달라지면 불안정한 오버클럭이나 메모리 설정(XMP)을 의심할 수 있습니다. 러너는 이 경우 경고하고 종료 코드 3을 돌려줍니다.

## 부하 모듈

| 모듈 | 내용 | 상태 |
|---|---|---|
| `int` | CRC-32, SHA-256, 정렬, 숫자 파싱 | 동작 (압축/해제는 추가 예정) |
| `fp` | 행렬곱(128×128), N-body(물체 256개), scalar/AVX2 경로 자동 선택 | 동작 (FFT·AVX-512는 미정) |
| `mem` | 읽기·쓰기·복사 대역폭, 캐시·DRAM 지연 (작업 크기를 바꿔 가며 L1→DRAM) | 동작 (SSE2) |
| `mt` | 원자적 연산 경합, 거짓 공유, lock-free 큐 | 동작 |

### 메모리 모듈 (`mem`)

| 측정 종류 (`--workload`) | 내용 | 표시 |
|---|---|---|
| `read` (기본) | 데이터를 읽어 합계 | GB/s |
| `write` | 고정 패턴 기록 | GB/s |
| `copy` | 원본 → 대상 복사. STREAM처럼 읽은 바이트와 쓴 바이트를 모두 셉니다 | GB/s |
| `latency` | 무작위 순서로 이어진 포인터를 따라가기. 다음 주소를 알려면 앞 로드가 끝나야 해서, 로드 1회 시간이 곧 지연입니다 | ns |

- `--size`는 전체 스레드가 다루는 데이터 크기입니다(기본 256 MiB, L3보다 충분히 큼). 스레드마다 같은 크기 구간을 맡고, `copy`는 원본·대상이 절반씩입니다.
- `sweep`으로 크기를 2배씩 늘리면 L1 → L2 → L3 → DRAM 구간에서 값이 계단처럼 바뀝니다.
- 알아 둘 점
  - 지연은 4 KiB 페이지 기준이라, 수 MiB를 넘으면 TLB 미스 비용이 포함됩니다(L3 안이라도 값이 커짐). 큰 페이지는 관리자 권한이 필요해서 쓰지 않습니다.
  - 대역폭 커널은 지금 SSE2(16바이트)입니다. DRAM 구간에는 충분하지만 L1·L2 구간은 CPU 연산 폭이 한계라 실제 캐시 대역폭보다 낮게 나옵니다. AVX2 경로는 FP 모듈과 함께 추가할 예정입니다.

개발 PC(i5-14400F) 실측 예:

| 항목 | 싱글 스레드 | 16스레드 |
|---|---|---|
| 읽기 256 MiB | 22.3 GB/s | 81.7 GB/s |
| 쓰기 256 MiB | 15.7 GB/s | 49.3 GB/s |
| 복사 256 MiB | 25.2 GB/s | 64.6 GB/s |
| 지연 256 MiB | 94.3 ns | |

### 동기화 모듈 (`mt`)과 확장 곡선 (`scale`)

| 측정 종류 (`--workload`) | 내용 |
|---|---|
| `shared` (기본) | 모든 스레드가 카운터 하나를 원자적으로 +1 (캐시 라인 하나를 서로 빼앗음) |
| `padded` | 스레드마다 자기 카운터 +1, 카운터끼리 64바이트 떨어뜨림 (경합 없는 기준) |
| `falseshare` | 스레드마다 자기 카운터 +1, 카운터 8개를 한 캐시 라인에 붙여 둠 (거짓 공유) |
| `queue` | lock-free 큐(Vyukov MPMC)에 64개 넣고 64개 빼기 반복 |

- 스레드끼리 섞이는 것 자체를 재므로 작업 단위 결과가 매번 다릅니다. 그래서 측정이 끝난 뒤 합계로 확인합니다(카운터 값 = 센 횟수, 큐에 넣은 값의 합 = 뺀 값의 합). 다르면 종료 코드 3.
- `cpu-bench-runner scale <모듈> [--workload W] [--to N]`: 같은 측정을 스레드 1개부터 N개(기본: 논리 CPU 수)까지 늘려 가며 반복하고, 새로 붙은 스레드의 코어 종류(P/E/SMT), 처리량, 1스레드 대비 배수, 스레드당 효율을 보여 줍니다. 모든 모듈에 쓸 수 있습니다.

개발 PC(i5-14400F, 16스레드) 실측 예: `padded` 19.3억 회/초, `falseshare` 8천만 회/초(24배 느림), `shared` 7천4백만 회/초, `queue` 740만 개/초. 정수 모듈 확장 곡선(4회 중앙값)은 성능 코어 6개 5.6배 → 효율 코어 4개 추가 8.9배 → 하이퍼스레딩 6개 추가 12.0배. 1스레드 값이 실행마다 10% 가까이 흔들려 배수도 그만큼 달라집니다.

## 화면 앱 (`app/`, 개발 중)

WPF(.NET 8) 앱입니다. 측정은 앱이 옆 폴더의 `cpu-bench-runner.exe`를 실행하고 `--json` 출력을 읽어서 합니다(점수 측정 진행률은 `--progress`로 stderr에 한 줄씩). 측정 프로그램이 따로 돌기 때문에 측정 중 화면 그리기가 끼어들지 않고, 측정 쪽이 멈춰도 앱은 살아 있습니다.

- PC 정보(CPU, 메모리 구성), **환경 점검**, **점수 측정**(싱글·멀티), **쓰로틀링 검사**(1분), **부동소수점**·**멀티코어**(확장 곡선·동기화, 점수 미반영)
- 진단 결과는 한국어로 보여 주고, 전원 관련 항목은 Windows 설정 화면으로 연결만 합니다(설정을 직접 바꾸지 않음).
- 빌드: C++ 쪽을 먼저 빌드한 뒤 `dotnet build app -c Release`. 러너와 모듈 DLL이 앱 출력 폴더로 복사됩니다.

## 빌드

필요한 것: Visual Studio 2022 Build Tools (C++ 데스크톱 워크로드, CMake 포함). clang-cl 빌드도 지원합니다.

```
cmake --preset msvc
cmake --build --preset msvc
ctest --preset msvc
```

결과물은 `build/msvc/bin/`에 생깁니다.

## 사용법

```
cpu-bench-runner info                       # CPU, 코어 구성, 캐시, 메모리(슬롯·채널·속도)
cpu-bench-runner check                      # 측정 전 환경 점검: 전원, 전원 관리 옵션, 백그라운드 CPU 사용률
cpu-bench-runner clock                      # 코어별 실제 클럭(유효 클럭)
cpu-bench-runner throttle                   # 60초 지속 부하 중 처리량·클럭 변화(쓰로틀링 검사)
cpu-bench-runner score                      # 싱글·멀티 점수 (점수 체계 v2)
cpu-bench-runner run int                    # 싱글 스레드 (성능 코어 고정)
cpu-bench-runner run int --mt               # 모든 논리 코어
cpu-bench-runner run int --threads 4 --duration-ms 3000 --runs 7 --json
cpu-bench-runner run mem --workload read --mt   # 메모리 읽기 대역폭, 모든 논리 코어
cpu-bench-runner run mem --workload latency --size 64M
cpu-bench-runner sweep mem --workload latency   # 16 KiB → 512 MiB 지연 곡선
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--threads N` / `--mt` | 1 | 스레드 수 / 전체 논리 코어 |
| `--duration-ms N` | 2000 | 측정 1회 길이 |
| `--runs N` | 5 | 측정 횟수 (워밍업 1회 별도) |
| `--seed N` | 1 | 입력 데이터 seed |
| `--no-pin` | | 코어 고정 끄기 |
| `--json` | | JSON으로 출력 (제어 앱·자동화용) |
| `--workload W` | 모듈 기본값 | 측정 종류 (`mem`: read, write, copy, latency) |
| `--size N` | 모듈 기본값 | 작업 데이터 크기. `16K`, `256M`, `1G`처럼 씁니다 (1024 단위) |

`sweep`은 `--size` 대신 `--from`(기본 16K), `--to`(기본 512M)를 받고, 측정 1회 500 ms × 3회가 기본입니다.

종료 코드: `0` 정상, `1` 실행 오류, `2` 사용법 오류, `3` checksum 불일치

## 측정 전 환경 점검 (`check`)

점수가 낮게 나오는 흔한 원인을 측정 전에 확인합니다. **읽기만 하고 설정은 바꾸지 않습니다.**

| 항목 | 경고 조건 |
|---|---|
| 전원 | 배터리로 동작 중 (노트북은 배터리에서 클럭을 낮춤) |
| 전원 관리 옵션 / 전원 모드 | 절전, 또는 Windows 전원 모드가 "최고의 전원 효율" |
| 최대 프로세서 상태 | 100% 미만 (보통 터보 부스트가 꺼짐) |
| 유휴 상태 CPU 사용률 | 3% 초과 (그만큼 멀티스레드 점수가 떨어질 수 있음). 사용률이 높은 프로세스 상위 5개를 보여 줌 |
| 메모리 채널 | 모듈이 1개(싱글 채널)이거나, 2개 이상인데 모두 같은 채널 슬롯에 꽂힘 |
| 메모리 속도 | 파트 번호로 읽은 정격 속도보다 낮게 동작 (XMP/EXPO 꺼짐 의심), 또는 모듈 자체 기본 속도보다 낮음 |

메모리 정격 속도는 SMBIOS로는 알 수 없어서(보통 JEDEC 기본 속도만 나옴), 주요 제조사 파트 번호 규칙으로 읽습니다: G.Skill, Kingston FURY/HyperX, Corsair, TeamGroup, Crucial, ADATA XPG, Patriot. 모르는 형식이면 판정하지 않습니다.

프로세스 사용률은 작업 관리자와 같은 방식(`NtQuerySystemInformation`)으로 읽어서, 일반 권한으로 열 수 없는 시스템 프로세스와 백신도 포함됩니다. 프로세스 목록은 화면에만 표시하고 어디에도 보내지 않습니다.

## 유효 클럭 (`clock`)

드라이버 없이 "지금 실제로 도는 클럭"을 잽니다. 앞 덧셈이 끝나야 다음 덧셈을 할 수 있는 의존 덧셈 체인은 1사이클에 1개씩만 실행되므로, 덧셈 수 ÷ 걸린 시간 = 클럭입니다([runner/clockchain.asm](runner/clockchain.asm). C++로 쓰면 컴파일러가 덧셈을 하나로 합쳐 버려서 어셈블리로 둠).

- 쉬던 코어는 부하를 받고 최고 클럭까지 올라가는 데 5~13 ms가 걸려서, 코어마다 30 ms 동안 먼저 부하를 건 뒤 100 ms 동안 잽니다.
- 최댓값과 중앙값을 보여 줍니다. 백그라운드 작업 등으로 중앙값은 측정할 때마다 달라질 수 있습니다.
- 개발 PC(i5-14400F) 실측: P코어 최대 4.59~4.69 GHz(사양 4.7), E코어 3.49 GHz(사양 3.5).

## 짧은 쓰로틀링 검사 (`throttle`)

모든 논리 코어에 정수 부하를 60초 동안 걸고, 1초마다 처리량을, 스레드마다 0.25초마다 유효 클럭을 잽니다(덧셈 체인을 부하 사이에 0.5 ms씩 끼워 넣음).

- 시작 구간(2~7초)과 끝 구간(마지막 1/3, 최대 10초)을 비교해서, **처리량이나 성능 코어 클럭이 5% 넘게 떨어지면** 쿨러·BIOS 전원 제한을 확인하라고 경고합니다.
- 클럭은 평균 대신 중앙값을 씁니다. 측정 도중 다른 프로그램에 잠깐 밀린 회차가 낮게 나와서, 평균을 쓰면 ±3%쯤 흔들렸습니다.
- 효율 코어 클럭만 내려가고 처리량은 그대로인 경우는 경고 대신 안내만 합니다. 개발 PC에서는 부하를 약 50초 넘게 이어서 걸면 E코어가 3.49 → 3.29 GHz로 내려갔지만(P코어 4.01 GHz 유지), 처리량 차이는 2% 이내였습니다. 2분 쉬고 45초만 걸면 내려가지 않았습니다.
- 모든 코어를 오래 쓰므로 프로세스 우선순위는 보통으로 둡니다.

## 점수 (`score`, 점수 체계 v2)

점수는 **싱글**과 **멀티** 두 개입니다. 항목마다 측정값을 기준값 대비 비율로 바꾸고, 비율들의 기하평균 × 1000이 점수입니다.

| 점수 | 항목 | 기준값 (= 1000점) |
|---|---|---|
| 싱글 (성능 코어 1개) | 정수 | 1,000 unit/s |
| | 메모리 읽기 256 MiB | 20 GB/s |
| | 메모리 지연 256 MiB (작을수록 좋음) | 100 ns |
| | 행렬곱 128×128 (부동소수점) | 5,000 unit/s |
| | 물체 256개 인력 계산 (부동소수점) | 5,000 unit/s |
| 멀티 (모든 논리 코어) | 정수 | 10,000 unit/s |
| | 메모리 읽기 256 MiB | 50 GB/s |
| | 행렬곱 128×128 (부동소수점) | 50,000 unit/s |
| | 물체 256개 인력 계산 (부동소수점) | 50,000 unit/s |

- 기준값은 **특정 PC가 아니라 고정된 숫자**입니다. 보기 좋게 반올림한 값일 뿐 특별한 의미는 없고, 한 번 정한 값은 바꾸지 않습니다. 바꿔야 하면 점수 체계 버전을 올리고, 버전이 다른 점수끼리는 비교하지 않습니다.
- 기하평균이라 한 항목만 유난히 높아도 점수가 크게 튀지 않습니다.
- checksum이 한 번이라도 어긋나면 점수를 내지 않습니다.
- 항목마다 워밍업 1회 + 5회 측정의 중앙값을 씁니다. 측정 회차 동안 다른 프로그램이 CPU를 7% 넘게 쓰면 그 회차는 버리고 다시 잽니다(항목당 최대 5번). 그래도 방해가 남으면 결과에 표시합니다. 개발 PC에서 바쁜 프로그램 하나(16개 코어 중 1개)만 띄워도 싱글 정수가 평균 2.8% 떨어져서 기준을 7%로 정했습니다. 싱글 항목은 측정하는 코어의 **하이퍼스레딩 짝**이 10% 넘게 바빴던 회차도 다시 잽니다. 짝이 바쁘면 행렬곱 싱글이 절반 가까이 떨어지는데, PC 전체 사용률로는 6%대로만 보여서 위 기준에 걸리지 않았습니다(버그 018).
- 결과 서버가 생기면 "같은 CPU 사용자 중 몇 %"도 함께 보여 줄 예정입니다.
- **v2(0.8.0부터)**: v1의 다섯 항목에 부동소수점 네 항목을 더했습니다. 기준값이 같은 앞 다섯 항목도 점수 계산에 들어가는 항목 수가 달라져서 **v1 점수와 v2 점수는 비교할 수 없습니다**. 앱의 기록에는 버전이 함께 표시됩니다.
- 멀티코어 동기화 측정(`mt` 모듈)은 코어가 많을수록 값이 낮아지는 측정이라 점수에 넣지 않고 앱의 멀티코어 카드에서 따로 보여 줍니다.
- 부동소수점 항목은 CPU가 AVX2를 지원하면 AVX2, 아니면 하나씩 계산하는 경로로 잽니다. 어느 경로였는지는 결과 JSON의 `variant`에 남습니다.
- 개발 PC(i5-14400F, DDR5-5600 ×2): v2 싱글 1497, 멀티 1615 (v1 때 싱글 1199, 멀티 1650). 측정에 약 2분 걸립니다.

## 개인정보

러너는 아무것도 전송하지 않습니다. `info`의 메모리 정보는 SMBIOS에서 읽는데, 모듈의 시리얼 번호와 자산 태그는 읽지 않습니다. 결과 업로드 기능이 생기더라도 시리얼 번호, 컴퓨터 이름, 계정명, IP는 수집하지 않고, 보내기 전에 전송 내용을 보여 주고 동의를 받을 예정입니다.
